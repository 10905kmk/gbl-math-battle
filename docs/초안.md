# GBL 부스 프로젝트 정리 — 수학 도형 무기 온라인 베틀 (36조)

## 1. 개요

- **행사**: 대전대신고등학교 GBL, 2026년 8월 14일(금)
- **팀명**: 36조 — 수학 도형 무기 온라인 베틀
- **컨셉**: AI × 수학 도형을 결합한 무기 제작 및 대전 체험 부스
- **부스 체험 시간**: 20분/팀 (5명 단위 입장)

## 2. 체험 흐름 (동시 진행 방식)

```
도형 학습 → 무기 제작 및 스탯 부여 → 웹 게임 대전 → 결과물 보관 → 감사합니다
```

- 참가자 5명이 **하나의 세션(코호트)** 으로 묶여 동시에 단계를 이동
- 서버가 전체 진행 단계(stage)를 하나만 관리하고, 관리자가 다음 단계로 넘기면 5대 기기가 동시에 화면 전환
- 단, **결과물(도형/무기/스탯)은 참가자별로 다름** — 동시 전환이어도 결과 화면은 개인별로 분기해서 렌더링
- 단계별 제한시간(학습/제작/대전/결과)을 두고 자동 전환, 미완성 참가자는 기본 스탯으로 자동 마감 처리

## 3. 시스템 아키텍처

- **로컬 서버(노트북)**: 부스 현장 와이파이 안에서 참가자 기기 5대와 웹소켓(Socket.io)으로 통신, 게임 로직과 AI API 프록시 역할
- **외부 AI API**: 참가자의 자연어 설명을 받아 도형 기반 무기·갑옷으로 구현
- **클라우드 저장소(Supabase 추천)**: 로컬 서버가 완성된 결과(도형/스탯/이미지 파라미터)를 저장 — 부스가 끝나도 결과 유지
- **결과 확인 페이지(Vercel 별도 배포)**: 저장된 id로 조회 가능한 상시 페이지, 참가자에게 QR/링크로 제공
- **관리자 페이지**: 세션 시작/단계 진행/강제 리셋/에러 로그 확인용, 고정 비밀번호로 최소 인증

핵심 설계 원칙:
- 로컬 서버가 AI API·클라우드 저장소 양쪽과 통신하므로 인터넷 연결 필요 (LAN 고립 아님)
- API 키(AI, Supabase)는 로컬 서버에만 두고 브라우저에 노출하지 않음
- 결과물 이미지까지 저장하려면 Supabase Storage 등 오브젝트 스토리지 별도 필요

## 4. 언어 및 기술 스택

- **전체 JavaScript로 통일** (도형 로직을 프론트/백엔드가 그대로 공유하기 위함)
- 백엔드: Node.js + Express (REST, AI API 프록시) + Socket.io (실시간 세션/대전)
- 프론트: **번들러 없이 CDN에서 Preact + htm을 직접 import** (`<script type="module">`)
  - `https://esm.sh/preact`, `https://esm.sh/preact/hooks`, `https://esm.sh/htm` 사용
  - stage 전환 시 화면을 통째로 다시 그려야 하고, 슬라이드 카드/무기 카드/진행도 표시 등 재사용 UI가 많아 컴포넌트+상태관리 이점이 필요해서 채택
  - npm 설치·Vite 빌드 스텝 없이 기존 폴더 구조·로컬 서버 서빙 방식 그대로 유지
  - 부스 현장 오프라인 대비: CDN 파일을 사전에 받아 `frontend/vendor/`에 넣고 로컬 서버가 서빙하는 방식도 검토 필요
- 데이터 저장: Supabase (테이블 자동 REST API, 별도 백엔드 라우트 최소화)
- QR 코드: 클라이언트에서 `qrcode.js` 등으로 즉석 생성 (백엔드 로직 불필요)

## 6. 관리자 페이지 기능 (최소 범위)

1. 세션 시작 — 새로 입장한 5명 등록 후 학습 단계로 broadcast
2. 다음 단계 진행 — 버튼 또는 타이머로 전체 동시 전환
3. 낙오자 강제 진행 — 제작 단계 시간 초과 시 기본 스탯으로 자동 마감
4. 강제 리셋 — 특정 기기 문제 시 관리자가 원격 리셋
5. 에러 로그 뷰 — AI API 실패/타임아웃 등 최근 로그 확인
6. 제출 현황 — Supabase 저장 건수/최근 결과 확인
7. 최소 인증 — `.env`의 `ADMIN_PASSWORD` + 간단한 세션 쿠키

## 7. 화면별 상세 구조

공통: 참가자 5대 기기는 서버가 broadcast하는 `stage`를 구독해 화면을 자동 전환한다(`app.js`). 결과물(도형/무기/스탯)은 참가자별로 다르므로, 같은 stage여도 렌더링은 개인별로 분기한다.

### ① 학습 (`screens/learn.js`)

- 슬라이드 카드: 제목 + 이미지 + 설명 텍스트로 구성된 순수 정보 전달형. 참가자 상호작용(퀴즈 등) 없음 — 수학 깊이는 슬라이드 콘텐츠(`content/shapes-slides.json`) 자체를 보강해서 확보한다.
- 슬라이드 넘김은 **관리자가 전체 동기화로 진행**한다(발표하듯 진행). 서버 상태 `stage='learn'`, `slideIndex`는 코호트 전체 공통이고, 클라이언트는 수신만 하며 별도 로컬 상태를 갖지 않는다.
- 진행도 표시(예: 3/6) 정도만 화면에 노출.

### ② 제작 (`screens/create.js`)

- 2단계 구성:
  1. **도형 선택** — 학습한 도형/프랙탈 목록을 그리드로 제시, 참가자가 하나 선택
  2. **자연어 설명 입력** — "이 도형으로 어떤 무기를 만들까요?" 텍스트 입력 + "생성하기" 버튼
- AI 응답 대기 중에는 로딩 화면 노출.
- **AI 실패/타임아웃 시**: 내부적으로 1회 자동 재시도 → 그래도 실패하면 선택한 도형의 "기본 무기"(고정 스탯, 특수효과 없음)로 자동 대체하고 다음 단계로 진행. *(잠정 결정 — 변경 가능)*
- **생성 결과 확정 방식**: AI 응답이 오면 자동 확정, 재생성/재시도 버튼은 제공하지 않음. *(잠정 결정 — 변경 가능)*
- 확정 후에는 "대기 중" 화면으로 전환: 자신의 무기 카드(이름/이미지 미니카드) + "다른 도전자를 기다리는 중... (N/5 완료)" 표시. 전원이 완료되면 서버가 `stage='battle'`을 broadcast해 전체가 동시에 넘어간다.

### ③ 대전 (`screens/battle.js`)

- **미정** — 대전 형식(페어링 방식, 실시간 액션 vs 스탯 기반 자동전투 등) 자체가 아직 팀 내부에서 결정되지 않아 브레인스토밍 보류. 별도 논의 후 재설계 필요.

### ④ 결과 (`screens/result.js`)

- 현장 기기 화면에는 **요약 정보만** 노출: 무기 요약(이름/이미지/스탯) + 대전 결과(승/패) + QR코드. 상세 페이지는 별도.
- QR은 `result-page`(Vercel, 상시 접속)로 연결되며, 그 페이지는 현장 화면과 **동일한 수준의 요약을 영구 소장**하는 용도다(전투 로그 등 풍부한 상세 페이지는 범위 밖).
- 다음 참가자를 위해 화면을 빨리 비워야 하므로 상세 정보를 현장 화면에 쌓지 않는다.

### ⑤ 감사 (`screens/thanks.js`)

- 감사 메시지 + **QR코드를 계속 유지 표시**(결과 화면 내용이 이어짐 — 아직 스캔 못 한 참가자를 위한 마지막 기회).
- **자동 리셋 아님** — 관리자가 다음 세션을 수동으로 시작하기 전까지 화면이 유지된다. (초안 2번 "자동 전환" 설명 중 감사 단계는 예외로 취급)

### ⑥ 관리자 페이지 (`admin/`)

- **공통 상단바**(모든 stage에서 항상 노출): 현재 stage, 남은 시간, 참가자 진행도(N/5 완료), 세션 시작·전체 강제 리셋 버튼.
- **본문은 stage에 따라 전환**:
  - `stage='learn'`일 때: PPT 발표자 모드를 본뜬 UI — 현재/다음 슬라이드 미리보기 + 이전/다음 슬라이드 버튼.
  - 그 외 stage(`create`/`battle`/`result`/`thanks`): 대시보드형 — 참가자별 진행 상태 리스트, 낙오자 강제 진행, 에러 로그, 제출 현황.
